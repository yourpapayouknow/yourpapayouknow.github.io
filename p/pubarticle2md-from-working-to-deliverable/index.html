PubArticle2MD 项目复盘：从“能跑”到“可交付”

一次真实的工具落地过程：需求、踩坑、修复、封装与发布

2026-05-04
阅读时长: 4 分钟

这次做 PubArticle2MD，最开始我以为是一个标准小工具项目：写完功能，收工。

真正做下来才发现，它更像一次完整的产品交付演练。不是“代码能跑”就结束，而是要让陌生用户在自己的电脑上，低门槛、稳定地用起来。

这篇就按真实时间线复盘：从第一版上线，到线上 404、桌面版“空壳”、打包环境缺失，再到最终可发布、可复现。

项目最初目标

当时定了 4 件事：

  1. 参考 wechat2pdf 思路，做公众号文章转 Markdown/PDF。
  2. 支持本地运行，尽量不把内容交给第三方。
  3. 提供 PWA 在线入口（GitHub Pages 可直接访问）。
  4. 尽可能提供普通用户可双击运行的 EXE。

测试文章： https://mp.weixin.qq.com/s/5BOAnJ5H4seYxSbXWi5Ibg

第一版：先把链路跑通

架构拆成两层：

  • 前端（PWA）：输入链接、选择抓取模式、预览、下载 Markdown/PDF。
  • 后端（Node API）：/api/health、/api/parse、/api/export/markdown、/api/export/pdf。

PDF 交给 Playwright 做服务端渲染，目标是稳定优先。

核心文件：

  • app.js
  • index.js
  • main.js

到这里“功能看起来都在”，但真正的问题才刚开始。

第一个坑：GitHub Pages 404

现象

仓库配好了，Pages 地址却直接 404： There isn't a GitHub Pages site here.

排查与根因

查了 Actions 和部署日志后确认：不是前端资源丢了，而是 Pages 发布链路没有被完整激活，导致工作流存在但站点状态不可用。

处理

  1. 校验仓库 Pages 配置。
  2. 重新触发部署。
  3. 部署后回测 URL。

最终在线入口恢复： https://yourpapayouknow.github.io/PubArticle2MD/

第二个坑：有 Action，不等于用户能用

你当时一句“这些 Action 意义不明”，其实特别关键。

它直接把目标从“工程师视角的流程完整”，拉回到“用户是否能直接打开页面并转换”。

后续就把工作流职责收敛为：

  1. CI 负责基础检查。
  2. Deploy GitHub Pages 专注发布 public/。
  3. README 把路径讲清楚，避免“看起来很复杂，实际不知道该点哪里”。

第三个坑（最关键）：EXE 其实只是前端壳

用户反馈

  • 选本地 API 报错：没有本地 API 服务。
  • 页面一直显示：纯前端模式（GitHub Pages）。

为什么会这样

当时桌面入口只做了 loadFile(index.html)，没有真正启动后端。

而前端会通过 ./api/health 探测本地服务，探测失败就永久判定为纯前端模式。

这说明 EXE 只是把网页包起来了，没有把“本地能力”打进去。

关键修复

  1. Electron 主进程启动本地 API（host=127.0.0.1，port=0 自动分配）。
  2. 窗口优先 loadURL(localApi.url)，失败才降级加载本地 HTML。
  3. 退出时关闭 server，避免僵尸进程。
  4. /api/health 增加 runtime 字段，前端据此展示真实运行模式。

这个改动之后，EXE 才从“演示壳”变成“可用工具”。

第四个坑：能启动还不够，环境必须随包

你当时提醒“本地打包再上传 release”，这句话非常对。

因为桌面应用要可靠，至少要解决两件事：

  1. 后端代码进包。
  2. Playwright Chromium 随包可用。

实际处理

  1. build.files 加入 server/**/*。
  2. 增加 ensure-playwright-browsers.js，打包前检查并安装 Chromium。
  3. 用 extraResources 把浏览器资源带进安装包。
  4. 启动时设置 PLAYWRIGHT_BROWSERS_PATH 指向 resources/playwright-browsers。
  5. 排除 asar 内重复资源，避免体积翻倍。

第五个坑：Windows 本地发布首次失败

现象

npm run release:local -- --tag v1.0.2 首次失败，卡在 npm.cmd run desktop:dist。

根因

Windows 下子进程执行 .cmd 的兼容性处理不稳。

修复

在 release-local.js 的执行器里对 Windows 启用 shell: true，再次执行即成功。

新版本发布： https://github.com/yourpapayouknow/PubArticle2MD/releases/tag/v1.0.2

最终结果

现在这个项目已经不是“能展示”，而是“可交付”：

  1. 在线模式可用（Pages 正常）。
  2. EXE 内置本地 API，不再是前端壳。
  3. PDF 依赖环境随包封装。
  4. 本地打包 + Release 上传流程可复现。
  5. 文档按真实使用路径重写，新用户能跟着跑通。

使用方式（对外可直接贴）

在线版（无需安装）

地址： https://yourpapayouknow.github.io/PubArticle2MD/

步骤：

  1. 输入公众号链接。
  2. 若直连失败，切换“代理 URL”或“粘贴 HTML”。
  3. 点击解析。
  4. 下载 Markdown ZIP 或 PDF。

示例链接： https://mp.weixin.qq.com/s/5BOAnJ5H4seYxSbXWi5Ibg

桌面 EXE（普通用户推荐）

  1. 打开 Release： https://github.com/yourpapayouknow/PubArticle2MD/releases/tag/v1.0.2
  2. 下载并运行 EXE。
  3. 看到“本地 API 模式（桌面 EXE 内置后端）”即可。

这次最重要的收获

这次最有价值的，不是“我又做了一个工具”，而是把工具做成了真正可交付的产品：

  • 在线可用。
  • 桌面可用。
  • 本地可复现。
  • 发布可持续。

其中最关键的一步，其实来自用户反馈：

“EXE 只是壳，环境没有封进去。”

这类反馈往往不华丽，却最能决定一个项目到底停在演示，还是走向真正可用。
