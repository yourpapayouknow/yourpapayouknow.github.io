XHSContentFetcher 项目复盘：从空仓到可发布 CLI

一次真实工程落地：从需求拆解到联调、修复和发布

2026-05-05
阅读时长: 4 分钟

这篇文章记录 XHSContentFetcher 的完整过程。

目标不花哨，但链路很长：输入小红书链接，抓正文和评论，下载图片或视频，做 OCR 和关键帧，再生成可以直接放进 Obsidian 的学习笔记。

1. 起点很干净，也很硬

项目刚开始时，仓库里几乎只有 计划.md、LICENSE、虚拟环境和 IDE 文件。

也就是说，没有现成代码可以改，只能从零开始搭。

我一开始做了两件事：

  1. 先把验收标准写死：必须是 CLI、必须支持图文和视频、必须能落到 Obsidian。
  2. 先做最小可行验证，不急着写大框架。

2. 先做“可用性验证”，再谈工程设计

我先查了我最初准备参考的仓库，结果只有 LICENSE，没法复用。

然后改用 xiaohongshu-cli 做底层能力验证，重点确认四个点：

  1. 能拿到 note_detail。
  2. 能拿到评论和子评论。
  3. 视频能拿到有效流地址。
  4. 有 HTML 回退，不用自己做签名逆向。

用真实 Cookie 和真实分享链接跑通后，才正式开始搭工程。

这个顺序很重要。先验证，再封装。否则后面大概率返工。

3. 工程怎么拆

第一版按职责拆了 12 个模块：

  • 配置与 Cookie：config.py
  • URL 解析：url_parser.py
  • 抓取：fetcher.py
  • 媒体下载：media.py
  • 视频处理：video_tools.py
  • OCR：ocr_engine.py
  • LLM 生成：deepseek.py
  • Markdown 输出：markdown_writer.py
  • Obsidian 打开：obsidian.py
  • 工作流编排：workflow.py
  • CLI 入口：cli.py
  • 通用工具：utils.py

先补了三类基础单测：URL 解析、Cookie 解析、评论排序。

第一轮结果是 6 passed，之后修 URL 规则后变成 7 passed。

4. 真正费时间的是联调，不是写文件

4.1 子评论接口会偶发把流程打断

图文链路第一次跑就遇到：

API error: {"code": -1, "success": false}

最后定位到子评论抓取。详情和主评论都正常，部分子评论请求偶发失败。

修法很直接：

  • 子评论改成单条容错。
  • 某条失败就跳过，不中断主流程。

修完后，图文和视频链路都能完整走完。

4.2 图片被保存成 .bin

部分 CDN 响应没有可靠 Content-Type，图片就落成了 .bin。

这会连带影响两件事：

  1. Obsidian 预览体验差。
  2. OCR 识别流程不稳定。

修法是扩展名判定做分层回退：

  1. 先看文件魔数。
  2. 再看 Content-Type。
  3. 再看 URL 后缀。
  4. 最后才退回 .bin。

修完后，图片能稳定落成 .webp/.jpg/...。

4.3 OCR 的问题是“兼容性堆栈”

这块不是一个 bug，而是一串问题：

  1. 只装 paddleocr 不够，还要装 paddlepaddle。
  2. 不同版本参数不一致，show_log 和 cls=True 会踩兼容坑。
  3. oneDNN/MKLDNN 在部分环境报错。
  4. 中文路径会触发 Invalid argument。

修复策略是“多层回退”：

  • 初始化参数回退。
  • OCR 调用参数回退。
  • 兼容环境变量兜底。
  • 识别前复制到临时 ASCII 路径。

4.4 URL 解析有个很隐蔽的坑

新链接形态是 /discovery/item/<id>。

我自己的解析器最初把 note_id 取成了 item，结果详情为空。

修法：

  1. 优先匹配 24 位 ID-like 片段。
  2. 增加 discovery/item/<id> 特判。
  3. 保留 explore/<id> 和 item/<id> 兼容。

5. 最大的转折不是技术，是内容质量反馈

链路跑通后，我自己回看产物时马上发现了三个问题：

  1. 只是复述原文，缺少知识点解读。
  2. 图片堆在文末，不是图文内联。
  3. 口吻不对，不像“我的笔记”。

这条反馈很关键。它让我明确了一件事：项目不是“能生成文本”就结束，而是要生成“可读、可用、可复盘”的笔记。

后续我把策略改成两步：

  1. 强化提示词约束：第一人称、解释优先、按点拆解。
  2. 模板优先：严格读取根目录 Tempate.md，不再用硬编码模板。

同时把素材相对路径喂给模型，让图片和关键帧按段落内联，不再统一堆到末尾。

6. Obsidian 对接也有小坑

对接本身不难，难的是系统环境差异。

在 Windows 上抓 Obsidian 子进程输出时，出现过 UnicodeDecodeError。

修法很简单：stdout/stderr 重定向到 DEVNULL，避免编码读流问题。

之后实测能自动打开 Vault，写入路径也正常。

7. 发布前我做了哪些收尾

发布前做了三类清理：

  1. 删除测试中间产物（output/、缓存、__pycache__）。
  2. 重写 README，保留读者真正要走的路径。
  3. 脱敏处理，确保 Cookie 和 Key 不入库。

最后走完 git add -> git commit -> git push，远程分支可用，Actions 正常触发。

8. 这次复盘里最有用的三条经验

  1. 先验证外部依赖是否真的可用，再设计架构。
  2. 长链路项目要默认“局部失败可继续”，别追求一步到位全成功。
  3. 生成式能力一定要被模板和结构约束，否则产物很难稳定。

9. 下一步

下一版我会优先补三件事：

  1. 断点续跑。
  2. OCR/LLM 缓存（按 note_id + hash）。
  3. 结构化日志（阶段耗时和错误分类）。

一句话总结这次项目：

真正有价值的不是“我接了几个模型”，而是把整条链路做成了可定位、可修复、可复用的工程系统。
