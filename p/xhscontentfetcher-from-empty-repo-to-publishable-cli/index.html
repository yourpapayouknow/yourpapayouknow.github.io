3.2 我的定位路径

我没有直接改代码，而是先拆开验证：

  1. get_note_detail 单独调，成功。
  2. get_comments 单独调，成功。

3.3 修复动作

我在 fetcher.py 里改 _fetch_sub_comments：

  1. 改成单条容错。
  2. 单条失败就跳过。
  3. 不让局部失败中断主流程。

修复后复测：

  • 图文链路跑通。
  • 视频链路跑通。

关键产物验证：

  1. 视频下载成功，文件是 video_raw.mp4。
  2. 关键帧抽取成功，默认抽取 8 帧。
  3. 评论抓取成功。

4. 媒体与 OCR 深度修复：这部分最耗时

4.1 图片输出成 .bin

现象：

  1. 图片文件变成 image_01.bin。
  2. Obsidian 预览和 OCR 都受到影响。

根因：

  1. 部分 CDN 响应缺失可靠 content-type。

修复：

我在 media.py 加了魔数检测和扩展名回退顺序：

  1. 先看内容头，覆盖 JPEG / PNG / GIF / BMP / WEBP / AVIF
  2. 再看 Content-Type
  3. 再看 URL 后缀
  4. 最后才用 .bin

结果：

  1. 图片稳定输出为 .webp/.jpg/...。

4.2 OCR 初始化失败：缺底层依赖

现象：

1

dependency 'paddlepaddle' is not installed

处理：

1
2

venv\Scripts\python -m pip install paddleocr
venv\Scripts\python -m pip install paddlepaddle

4.3 PaddleOCR 参数兼容问题

我遇到两个典型兼容问题：

  1. 某些版本不接受 show_log。
  2. 新版在 OCR 参数里带 cls=True 时会抛 unexpected keyword。

修复策略：

  1. 初始化参数做多套回退。
  2. OCR 调用失败后回退到不带 cls 的方式。

4.4 oneDNN / MKLDNN 兼容报错

现象：

1

ConvertPirAttribute2RuntimeAttribute not support ...

修复：

  1. 在 ocr_engine.py 设置兼容环境变量，禁用问题路径。

4.5 中文路径导致 Invalid argument

现象：

  1. Paddle 在部分中文路径下读取文件失败。

修复：

  1. OCR 前先复制到临时 ASCII 路径。
  2. 识别完成后映射回原文件名。

4.6 OCR 文本污染

现象：

  1. OCR 结果混入临时路径字符串。

修复：

  1. 过滤 xhs_ocr_、盘符路径、tmp 路径行。

结果：

  1. OCR 文本可直接进入笔记。

4.7 OCR 超时不是功能失败

我实际还遇到过一次“超时中断”。

这次不是逻辑错误，而是首次全量 OCR 跑 8 张图时加载和推理时间偏长。

我采取的动作：

  1. 放宽命令超时窗口。
  2. 完整跑到底，再判断是否存在真实异常。

5. 提示词迭代：从“复述”改到“可读笔记”

链路跑通后，我回看产物，发现三个硬问题：

  1. 文本复述多，知识点拆解不够。
  2. 图片堆在文末，不是图文并茂。
  3. 口吻不像我的笔记。

5.1 第一次改造：强化提示词约束

我在 deepseek.py 做了三层调整：

  1. 固定第一人称口吻。
  2. 解释优先，要求按“是什么 / 为什么 / 怎么用 / 边界误区”拆解。
  3. 禁止教学腔、禁止空泛总结。

同时在 workflow.py 把素材相对路径直接喂模型：

  • assets/images/...
  • assets/frames/...
  • assets/video/...

目的很明确：模型必须内联引用，不允许文末堆图。

5.2 第二次改造：模板优先，禁用硬编码骨架

我后续把策略改成“模板优先”：

  1. 优先读取根目录 Tempate.md。
  2. 兼容 Template.md / template.md。
  3. 找不到模板就报错，不再自动生成章节骨架。
  4. 占位符替换真实路径：
    • assets.images[*].path
    • assets.video_frames[*].path

这一步的意义是：我把结构控制权从模型拿回到模板。

6. URL 解析事故：discovery/item/<id>

6.1 故障现象

新链接进入后，全链路失败：

1

[ERROR] 帖子详情为空，无法提取 note_card。

6.2 我的定位过程

我先用独立脚本验证，确认：

  1. XhsClient.get_note_detail 能拿到 items。
  2. 我自己的 url_parser 把 note_id 解析错了，取成了 item。

6.3 修复方案

我在 url_parser.py 做三点修复：

  1. 优先匹配 24 位 ID-like 片段。
  2. 特判 discovery/item/<id>。
  3. 保留 explore/<id> 和 item/<id> 兼容逻辑。

复测结果：

1

7.3 UnicodeDecodeError 修复

现象：

1

UnicodeDecodeError: 'gbk' codec can't decode ...

根因：

  1. subprocess 捕获 Obsidian 输出时发生编码读流问题。

修复：

  1. obsidian.py 把 stdout/stderr 改成 DEVNULL。

复测后恢复正常。

13. 我这次最值的三个决策

  1. 先做可用性验证，再做架构设计。
  2. 把长链路做成“局部失败不拖垮全流程”。
  3. 用模板约束生成结构，把质量控制权留在我手里。

14. 下一步优化计划

  1. 断点续跑，减少长任务重跑成本。
  2. OCR / LLM 缓存，按 note_id + 素材 hash。
  3. 结构化日志，覆盖阶段耗时和错误分类。
  4. 模板变量校验，缺失章节自动报错。
  5. “仅更新正文 / 仅更新评论”子命令。
  6. 多模型路由与失败回退策略。

15. 最终复盘一句话

这次我真正做成的，不是一个“能跑演示”的脚本，而是一条可定位、可修复、可复测、可发布、可复用的工程链路。
